# Architectural Decisions

Этот документ фиксирует ключевые архитектурные решения проекта.

## ADR-001: Модульная архитектура по доменам

**Дата:** 2026-07-28  
**Статус:** Принято

### Решение
Использовать доменную структуру:
```
feature/
├── core/        # Ядро: EventBus, Workspace, Profile, Plugin, History, Decision
├── desktop/     # Рабочее место оператора
├── recognition/ # Движки распознавания
├── search/      # Поисковые индексы
├── storage/     # Хранение: БД, логи, модели
├── import_/     # Импорт фотографий
├── plugins/     # Реализации плагинов
├── studio/      # Лаборатория (зарезервировано)
└── labs/        # Эксперименты (зарезервировано)
```

### Обоснование
- Разделение ответственности
- Независимая эволюция доменов
- Четкие зависимости: Desktop → Core → Recognition/Search/Storage

### Последствия
- Легче добавлять новые плагины
- Можно заменять Search/Recognition без изменения Core
- Desktop зависит от Core, но Core не зависит от Desktop

## ADR-002: Core слой как фундамент

**Дата:** 2026-07-28  
**Статус:** Принято

### Решение
Выделить Core как независимый слой с минимальными зависимостями.

### Компоненты Core
- EventBus
- WorkspaceManager
- ProfileManager
- PluginManager
- HistoryManager
- DecisionEngine

### Обоснование
- Core не зависит от GUI, БД или конкретных алгоритмов
- Все остальные модули зависят от Core
- Core можно тестировать изолированно

---

## ADR-003: Plugin API через Protocol

**Дата:** 2026-07-28  
**Статус:** Принято

### Решение
Использовать `typing.Protocol` для интерфейсов плагинов вместо ABC.

### Обоснование
- Protocol позволяет duck typing
- Меньше boilerplate
- Легче адаптировать существующий код под интерфейс

---

## ADR-004: EventBus для слабосвязанности

**Дата:** 2026-07-28  
**Статус:** Принято

### Решение
Использовать EventBus для коммуникации между модулями.

### Обоснование
- GUI не зависит напрямую от Recognition
- History слушает все события
- Легко добавлять новые подписчики

---

## ADR-005: Workspace как центральное понятие

**Дата:** 2026-07-28  
**Статус:** Принято

### Решение
Каждый workspace — это независимый архив с собственной БД, индексом, логами и профилями.

### Обоснование
- Поддержка нескольких баз без переписывания кода
- Быстрое переключение между архивами
- Изоляция данных

---

## ADR-006: Профили как отдельные файлы

**Дата:** 2026-07-28  
**Статус:** Принято

### Решение
Хранить каждый профиль в отдельном YAML-файле в `profiles/`.

### Обоснование
- Легко экспортировать/импортировать
- Можно версионировать
- Не нужно парсить один большой YAML

---

## ADR-007: DecisionEngine минимальный на старте

**Дата:** 2026-07-28  
**Статус:** Принято

### Решение
Реализовать только базовые стратегии (max, vote, hybrid), а Smart Vote и Adaptive Threshold отложить на v0.3+.

### Обоснование
- GUI покажет, какая информация реально нужна
- Не перегружать ядро преждевременно
- Лучше одна рабочая стратегия, чем пять не протестированных

---

## ADR-008: Desktop вместо GUI

**Дата:** 2026-07-28  
**Статус:** Принято

### Решение
Назвать слой Desktop, а не GUI, потому что это рабочее место оператора с панелями, очередями и workflow.

### Обоснование
- GUI — это только визуальная часть
- Desktop — это полноценный рабочий слой
- Правильный naming с самого начала

---

## ADR-009: Функциональный GUI сначала

**Дата:** 2026-07-28  
**Статус:** Принято

### Решение
Сделать минимально функциональный интерфейс, а не красивый.

### Обоснование
- После обработки 5-10k фото станет понятно, что realmente нужно
- Красивый GUI потом переделать дорого
- Функциональный GUI можно улучшать постепенно

---

## ADR-010: Operator Workflow перед GUI

**Дата:** 2026-07-28  
**Статус:** Принято

### Решение
Спроектировать сценарий работы оператора до написания GUI.

### Обоснование
- Вместо вопроса "какие кнопки добавить?" задаем "какой следующий шаг делает оператор?"
- GUI строится вокруг workflow, а не наоборот
- Снижает риск переделок

---

## ADR-011: HistoryManager с snapshot для отката

**Дата:** 2026-07-28  
**Статус:** Принято

### Решение
Каждое действие в истории хранит snapshot_before и snapshot_after.

### Обоснование
- Возможность отката любой операции
- Страховка от человеческих ошибок
- Основа для Undo/Redo в будущем

---

## ADR-012: ProfileManager с экспортом/импортом

**Дата:** 2026-07-28  
**Статус:** Принято

### Решение
Профили можно экспортировать в JSON и импортировать.

### Обоснование
- Обмен настройками между пользователями
- Резервное копирование конфигурации
- Легко делиться удачными конфигурациями

---

## ADR-013: Откладывание Studio и Constructor

**Дата:** 2026-07-28  
**Статус:** Принято

### Решение
Все экспериментальные идеи (Studio, Marketplace, Smart Vote, Black Box, Evolution Mode) отложить на v1.0+.

### Обоснование
- Сначала нужен стабильный рабочий инструмент
- Эксперименты ломают стабильность
- Архитектурное место уже заложено (`feature/studio/`, `feature/labs/`)
- Идеи формализованы в `docs/labs/` и `docs/IDEAS.md`
